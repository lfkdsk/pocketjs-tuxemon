# Feature status

What the Pocket Tuxemon port can do today, system by system.

- **Done**: on `main` and verified by a test, a journey replay or an upstream comparison.
- **Partial**: works within the limits noted.
- **Planned**: not on `main` yet. "In progress" means someone is working on it now.

Per-action numbers come from the import coverage report,
[reports/G1-coverage.md](../reports/G1-coverage.md). It is regenerated by `bun run import`.

| Music (`play_music`, `music_playing`, `fadeout_music`) | Partial | All 24 content-resolvable tracks are transcoded to 22.05 kHz mono QOA: 21 map `play_music` slugs plus the three battle/victory/defeat slugs named by all 40 environments. Staging is limited to one in-flight or ready file and 4 MiB, hands its buffer to the QOA decoder once, and drops its own reference immediately. The audio driver is replaced once when a requested file finishes, or once after a stale handoff is discarded so a later request can retry; existing streams and one-frame WAV cues keep syncing while handoff waits. A page failure is reported for that track without disabling other audio. `playBgm`/`fadeoutBgm`/`pauseBgm`/`resumeBgm` and the `bgmPlaying` condition are mapped, so map music plays and its reducer state survives maps, saves and rewinds. `fadeout_music` sets `sys.music_fading` so `music_playing` is false immediately (matching upstream), while the audible fade finishes. Six authored map arguments (eight actions) are not music DB slugs and stay silent, matching upstream lookup. Environment battle/victory/defeat selection is not yet connected to the battle lifecycle, so those three files are packaged but unused there. `verify:audio` checks deterministic transcodes, hashes, duration and whole-track loop bounds; `verify:web:audio` streams three newly added tracks through a real Chrome AudioWorklet with non-zero PCM and no underrun |
